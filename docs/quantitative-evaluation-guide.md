# AIKA 量化评估与 README 图表操作指南

更新日期：2026-11-24。本文面向当前仓库中的完整投研系统，目标是在可复核的实验完成后，为 README 提供回答质量、组件作用和运行代价的图表。公开 MCP 示例知识包的效果需要另行评估，不能直接套用本实验结论。

## 1. 先确定现在能做什么

目前已有 20 道经过题目人工审核的 v2 开发题、A/B/E/F 实验运行器、独立评分和报告脚本。题目通过审核不等于系统答案已经通过审核，也不等于独立测试集。

- [20 题集中复核报告](../data/eval_runs/closeouts/review_20/user_consolidated_confirmation_20261124/report/report.md)：仍有 30 份答案含待核项、5 个严重错误候选待判，不能作为产品结论。
- [10 题双公司探索记录](../data/eval/resume_experiment/final_observations_20261124.md)：两轮 B/F 对照均有配置不符，整轮不满足有效对照条件，不可画成质量提升。
- [候选题整理和后续工作](../data/eval_runs/closeouts/continuation_20261124/progress.md)：历史题目能否作为独立测试题仍需检查。
- [完整实验协议](../data/eval/experiment_protocol_v1.md)：版本、评分与人工复核的详细定义。本文是操作指南；正式实验如要更改协议，须在运行前记录差异。

**最终交付：**一份冻结的评估协议和题集、一组可追溯的运行与人工审核记录、一份汇总报告，以及 README 中的三张图。所有数值来自实际实验；尚未完成的内容显示为待测。

## 2. 实施顺序和验收点

| 阶段 | 操作 | 完成标志 |
|---|---|---|
| 1. 整理历史问题 | 完成已有分歧和严重错误候选的复核；定位双公司题预算问题 | 有审核决定或明确的待核原因；修复仅用开发题检查 |
| 2. 建立题集 | 扩充开发题，准备独立测试题，核查事实和泄漏 | 每题有原文、要点、审核记录；测试集在运行前冻结 |
| 3. 冻结实验 | 固定代码、运行数据库、模型、参数、题目和评分口径 | 形成可重建的运行清单；小规模试运行无配置偏差 |
| 4. 生成与评分 | 各方案对同一批题运行，保存输出并独立评分 | 所有计划输出均有终态；失败和待核没有被删除 |
| 5. 人工复核 | 校准评审、复核分歧和严重错误、分层抽查 | 保存人工判断、分歧、抽样清单及未决数 |
| 6. 出图和发布 | 计算汇总数据，制作图表，写 README 和详细报告 | 每个数字可追溯；局限和成本与图一起展示 |

可先完成一轮**探索性小实验**熟悉流程，再准备正式测试；探索题、修复依据和测试题不能混称独立测试。

## 3. 设计题集

以 40 道开发题、60 道独立测试题作为首轮目标，而非宣称 60 题足以证明总体效果。按实际资料与审核能力调整；各类别题数在运行前固定，并在报告中列出。建议覆盖：事实查询、公司比较、产业链关系、数字/年份/口径、资料不足或冲突。可沿用现有四类 `simple_lookup`、`complex_analysis`、`numeric_conflict`、`insufficient_evidence`，在题目标签中细分产业链主题。

1. 从现有 QA/RAG 候选中选题，核查此前是否用于开发、调试、人工对照或提示设计。历史使用不明的题暂放开发组。RAG v1/v2 不是两套互不重叠的题。
2. 按公司、报告、原文事实和问题意图排查重复。高度重叠或共享关键事实的题作为一组划分，避免仅改写问题便进入测试集。记录实际重复与分组规则。
3. 参考 [v2 题目及审核清单](../data/eval/benchmark_v2_review.md)逐题写标准事实、PDF 页码和原文、关键必答要点、可接受的替代证据、禁止推断、可回答/不可回答边界及截止日期。不要把背景资料误设为必需证据。
4. 人工核对主体、时间、数值、单位、表头、脚注和证据是否真正支持结论。保存审核人、实际审核时间或明确标注意见录入时间、审核决定及内容哈希；修改内容后重新审核。
5. 被测系统只接收公开问题和统一任务要求；标准事实、答案要点、证据位置和评分标签留给评测端。

**结构检查示例**（在仓库根目录执行；以下第一条只适用于现有 20 题 pilot）：

```bash
.venv/bin/python scripts/validate_eval_benchmark.py --pilot --require-human-review
```

新题集准备好后，将下面的路径换成实际文件。第二条还需要本地私有 PDF、原文语料和相关依赖：

```bash
.venv/bin/python scripts/validate_eval_benchmark.py \
  --benchmark data/eval/benchmark_dev_frozen.jsonl \
  --additional-benchmark data/eval/benchmark_test_frozen.jsonl \
  --require-human-review

.venv/bin/python scripts/validate_eval_benchmark.py \
  --benchmark data/eval/benchmark_test_frozen.jsonl \
  --check-sources --require-human-review
```

上面两个 `*_frozen.jsonl` 是**需要创建的目标文件名**，不是仓库现成文件。结构检查无法证明题目独立、证据充分或答案正确；仍要保留人工审核和去重记录。资料或 PDF 不可公开时，只发布有权公开的元数据、哈希与可复核示例，不上传私有原文或密钥。

## 4. 固定方案，确认消融真的成立

当前运行器支持以下版本，实际含义以[实验协议](../data/eval/experiment_protocol_v1.md)和运行轨迹为准：

| 版本 | 行为 | 适合回答的问题 |
|---|---|---|
| A | 模型直接回答，不使用检索 | 与可获取外部资料的方案相比，结果有什么不同 |
| B | 一次向量检索后生成 | 基础 RAG 与完整流程整体有何不同 |
| E | 完整 Agent 生成原始答案，但不做最终答案质量干预 | 作为 F 的配对候选 |
| F | 在 E 的同一候选及证据上进行最终答案检查和必要干预 | 检查和干预对同一候选产生什么变化 |

B 与 F 对比的是整个流程，不可将差异归因于图谱或补检。E/F 共享候选，比较的是最终答案检查和干预的组合；共享调用实际账单只计一次，但作为独立任务估算 F 成本时应计入完整共享阶段。

图谱、补检等单组件消融目前**不能仅凭上述版本自动得到**。要做这些图，需要先实现并验证对应开关，确保仅目标组件变化，检查真实执行轨迹，再用同题运行。不要把关闭 Agent 的环境变量直接当作合格消融。若暂未实现，图 2 先做 E/F 的“答案检查与干预”比较，并如实标注。

## 5. 修复和冻结运行环境

1. 对照[双公司实验记录](../data/eval/resume_experiment/final_observations_20261124.md)，检查第 6 题的比较证据缺口判断、规划线索和调用预算；先在开发题修复和验证。不要预先认定预算耗尽的唯一原因。把旧运行保留为无效对照；修复后产生新运行。
2. 准备 Python 环境、模型和 Embedding 服务、PostgreSQL 检索索引及图谱。完整流程的具体启动要求见根目录 [README](../README.md)。确认模型和 embedding 可用，数据库内容、图谱、索引、来源日期与题集的语料范围一致。
3. 在测试前固定并记录：代码提交及工作区修改的补丁或快照、题集及哈希、运行时数据库/索引和图谱快照、模型与服务端标识、参数、提示版本、上下文预算、超时/重试、运行顺序、缓存和评分规则。不要将 API key 写入记录。
4. 在开发题做小范围试运行，核对各版本实际执行、上下文、输出数量与配置。变更代码、数据或参数后重新冻结；不要将不同配置的结果拼成同一轮。

先做无模型调用的预检查（默认题集为已审核的 20 道开发题；`--limit` 只用于试运行）：

```bash
.venv/bin/python scripts/run_experiments.py --variants A B E F --limit 2 --dry-run
```

`--dry-run` 只检查计划及题集读取，不验证实际模型调用、数据库连通性或真实运行轨迹。确认预算后，去掉 `--dry-run` 才会实际运行并可能产生费用。正式测试必须使用冻结测试集，不要保留 `--limit`。

## 6. 运行、评分和人工复核

### 6.1 生成答案

正式题集存在且完成前述审核后，执行：

```bash
.venv/bin/python scripts/run_experiments.py \
  --benchmark data/eval/benchmark_test_frozen.jsonl \
  --variants A B E F
```

记录输出中的 `output_dir`；运行目录包含题集、manifest、逐题输出和运行轨迹。检查 `manifest.json` 中的实际配置、题号、输出数量、异常和 `valid_for_comparison`。如果是 `false`，停止将该轮用于方法质量对比，记录原因；不要剔除异常题后宣布整轮有效。普通任务失败应按预先约定保留并计入失败统计；**配置不符**还需单独判断整轮比较是否有效。

脚本支持 `--resume` 续跑相同冻结条件下尚未完成的输出；它不是修改预算后把新结果混入旧运行的方式。检查帮助：

```bash
.venv/bin/python scripts/run_experiments.py --help
```

### 6.2 独立评分

把下面的 `实际生成目录` 替换为上一步输出的目录。先用规则模式检查流程；它不调用评分模型，语义项目仍会待核，不能作为最终成绩。

```bash
.venv/bin/python scripts/score_experiments.py \
  --run-dir 实际生成目录 --rules-only
```

正式模型辅助评分时去掉 `--rules-only`；这会产生模型调用和费用。保存输出的评分目录及计费信息，必要时按帮助说明导入人工审核文件。评分者看到的答案应匿名化，不把版本名称作为判断依据。模型意见必须经过校准和人工核查，不能直接称为人工审核结果。

```bash
.venv/bin/python scripts/score_experiments.py --help
```

### 6.3 人工审核

按实验协议先做 8 份答案的人工校准：四类任务各 2 份、四个版本各 2 份，并覆盖 E/F 同题输出。当前若只运行 B/F，不能声称满足这个 A/B/E/F 校准设计，应先明确并记录适用的校准方案。之后：

- 复核全部严重错误候选和版本判分分歧；核对回答、实际引用、原文、主体、年份和口径。
- 对其余答案按类别分层随机抽查 20%，每个非空类别至少 1 份，保存抽样种子、清单和审核人。
- 每项标记支持、错误/遗漏或待核及理由；无法判断就保留待核，不自动判正确或错误。记录人工与模型分歧及解决过程。
- 补充少量真实使用者的任务试用，记录完成时间、可用性与修改量；没有试用数据时不写“节省多少研究时间”。

以实际评分目录和输出目录生成报告：

```bash
.venv/bin/python scripts/report_experiments.py \
  --score-dir 实际评分目录 --output-dir 实际报告目录
```

报告生成 `report.md` 和 `comparison.json`。检查评分完成状态、待核和严重错误候选；脚本的就绪标志并不能代替对题集独立性、比较有效性及人工审核范围的检查。

## 7. 汇总指标：先统一分母，再画图

沿用现有协议和报告的口径：要点覆盖、引用正确率等先计算**每道适用且已判定题目的比例**，再对题目求平均，标出适用题数和待核项。不要把该值与“所有要点直接合并后的总覆盖率”混用；后者如另行采用，需要重新明确公式并从逐项数据计算。

| 指标 | 计算与边界 |
|---|---|
| 关键要点覆盖 | 每题正确必答要点 / 该题已判定必答要点，再取适用题均值；遗漏和错误不算命中 |
| 引用正确率 | 每题受到原文支持的引用配对 / 已判定引用配对，再取适用题均值；无引用为不适用，另报缺失引用题数，不能记满分 |
| 任务可用率 | 按协议列出可用、轻微修改、需大改、不可用及待核数量；若把轻微修改计入可用，需在图注明确 |
| 严重错误 | 至少有一项严重错误的题数 / 已判定题数，另列待核；不因没有检查就写零 |
| 端到端耗时 | 每方案计划题的墙钟耗时中位数及范围，分别标出失败数；F 含共享生成与后续检查 |
| 费用和调用 | 生成、评审分列；记录价格来源和用量，缺项标未知或不完整 |

运行失败按协议保留：任务不可用，预期要点未完成；没有答案时事实/引用指标不适用，不能因此解释成没有错误。资料不足题没有必需证据时，必需证据覆盖为不适用。汇总同题改善、持平、退步和待比较数量；报告百分比变化时区分**百分点**与相对变化。

注意当前 `report_experiments.py` 主要输出逐题均值和平均耗时；中位数、范围、逐项合并分母或图表不能直接从均值反推。要从 `results.jsonl`、`scores.jsonl` 的逐题/逐项记录另行计算并复核；先核对失败和重试是否完整纳入。若某项数据不能可靠恢复，标记未知，不绘制该指标。

## 8. 制作三张图

先把经审核的汇总数据整理为 CSV 或表格，至少保留：实验 ID、题集哈希、版本、指标、值、适用题数、失败数、待核数、单位、计算脚本或表格版本。各图都写清题集、范围、日期和方法；百分比柱状图从 0 开始，标注方向及分母。图中使用同一配色，避免 3D 效果。

1. **回答质量：分组柱状图。** 横轴为要点覆盖、引用正确率和任务可用率；颜色代表 A/B/F。A 没引用时显示“不适用”，并展示引用缺失，不把空值画成 0% 或 100%。旁边列严重错误与待核。图注写明评分和题目口径。
2. **方法作用：横向柱状图或同题配对图。** 先画已有 E/F 最终答案检查与干预对比；显示改善、持平、退步、待比较题数。图谱、补检等只在实现并验证单组件消融后分别加入，不把 B/F 差异归因于某个组件。
3. **质量与代价：散点图。** 横轴为端到端耗时中位数，纵轴为要点覆盖，每点一个方案；旁边列失败数、费用及是否完整。小样本展示题数和耗时范围，不能当作生产服务水平。

可以用熟悉的表格软件或绘图库制作，导出 `docs/imgs/eval-quality.png`、`eval-ablation.png`、`eval-tradeoff.png`；同时保存原始汇总表、绘图文件或脚本与生成命令。上述图片和绘图程序目前**尚不存在**，应在实验和人工审核完成后生成。只有一项指标无法核实时，保留其他可支持的图，并明确缺口。

## 9. 写入 README 并发布前检查

将“量化评估”放在现有项目展示之后，三图配一段精简说明：题集范围、样本量、截止日期、模型、与对照方案的差异，以及详细报告链接。可用下面模板，替换全部占位内容后再发布：

```markdown
## 量化评估

在 [N] 道 [独立测试 / 探索性开发] 题上，比较 [实际方案]。
题目覆盖 [类别]；资料截止 [日期]，评分方式为 [方式]。

![回答质量对比](docs/imgs/eval-quality.png)
![答案检查与干预对比](docs/imgs/eval-ablation.png)
![质量与耗时](docs/imgs/eval-tradeoff.png)

样本、失败与待核数量、完整配置及局限见 [评估报告](实际报告路径)。
```

发布前逐项确认：

- [ ] 正式结果来自运行前冻结且完成独立性审核的测试题；否则明确标“探索性”。
- [ ] 运行 `valid_for_comparison` 与实际轨迹均支持所述比较；异常、失败和待核未被隐藏。
- [ ] 图表每个数字均能回溯到原始运行、评分、人工判断及汇总口径；标出样本量和分母。
- [ ] 不将单一指标称为系统整体准确率，不将整体流程差异归因于未消融的组件。
- [ ] 耗时、费用、模型、语料和使用范围均有说明；未知费用没有记零。
- [ ] 报告与图片引用有效，公开材料不包含 API key、私有原文或无权发布的数据。
- [ ] 如结果持平或退步，如实展示，并区分观察结果与原因假设。
